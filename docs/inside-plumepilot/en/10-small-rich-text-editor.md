# 10 — A small rich-text editor

## `contenteditable`, Selection, Range, lists, and callouts

In Chapter 09, we saw that the HTML quiz generated by PlumePilot is not simply a document: it is a small offline application.

With version 2.35.0, that application gained another interesting feature: two note fields for each question—**Explanation** and **Observations**—became small rich-text editors instead of plain text boxes.

Users can apply bold, italic, underline, strikethrough, superscript and subscript; create bulleted and numbered lists, checklists, colored highlights, and callouts; hide text for review; insert mathematical symbols; undo and redo; use keyboard shortcuts; and mark the personal review status of a question.

At first this might look like a formatting problem:

```text
user presses B
    ↓
make text bold
```

But a rich-text editor must constantly answer harder questions:

```text
Where is the caret?
What is selected?
Does the selection still belong to this editor?
Did a toolbar click destroy the selection?
Are we inside a list, checklist, or callout?
Does highlighted text already have another color?
What should pressing Enter do?
Where should typing resume after Escape?
How do we persist HTML without allowing arbitrary markup?
How do we recreate the editor after a rerender?
```

Using `offline-quiz-runtime.js` as a case study, this chapter explains a fundamental idea:

> **A rich-text editor does not merely change a string. It changes a DOM tree, a selection, an editing state, and a persistable representation at the same time.**

---

# Part I — From `textarea` to `contenteditable`

## 1. Why a `textarea` is not enough

A normal `<textarea>` essentially stores a string:

```text
"This is my explanation"
```

We can easily inspect:

```js
textarea.value
textarea.selectionStart
textarea.selectionEnd
```

But the text has no HTML structure. We cannot naturally represent:

```html
<strong>this part</strong>
<ul>
  <li>point one</li>
  <li>point two</li>
</ul>
```

without inventing a custom format or exposing markup to the user.

With `contenteditable`, an ordinary DOM element becomes editable:

```js
const editor = document.createElement("div");
editor.contentEditable = "true";
```

PlumePilot creates two editors for each question:

```js
const editor = document.createElement("div");
editor.className = "note-editor";
editor.contentEditable = "true";
editor.setAttribute("role", "textbox");
editor.setAttribute("aria-label", labelText);
editor.setAttribute("aria-multiline", "true");
```

Historical reference:

```text
offline-quiz-runtime.js:470–490
```

The conceptual difference is enormous. In a textarea, the primary state is a **string**. In a `contenteditable` element, the visible content becomes a **tree**:

```text
editor
├── text
├── <strong>
│      └── text
├── <span class="highlight">
│      └── text
├── <ul class="checklist">
│      ├── <li>
│      └── <li>
└── <div class="callout">
       └── text
```

This immediately introduces the concept of a **document model**.

---

## 2. `contenteditable` is not a complete editor

Writing:

```html
<div contenteditable="true"></div>
```

does not mean we have built an editor. It only delegates some editing operations to the browser: inserting and deleting text, moving the caret, selecting content, keyboard composition, some paragraph/list management, and interaction with the browser's input system.

The browser also chooses many details of the generated DOM.

For instance, pressing Enter is not semantically equivalent to:

```js
editor.innerHTML += "<br>";
```

The result depends on whether the caret is inside a paragraph, list, list item, callout, inline node, or empty editor.

> **`contenteditable` provides an editing host, not a high-level data model.**

PlumePilot must build its own editing protocol on top of that behavior.

---

# Part II — Selection and Range

## 3. The caret is a collapsed selection

When we say "the caret is after this word," the browser represents that position through the Selection API.

PlumePilot reads it with:

```js
const selection = window.getSelection();
```

A `Selection` describes what the user has selected in the document. It may be non-collapsed:

```text
"this [part of the text] matters"
```

or collapsed:

```text
"this part| of the text"
          ↑
         caret
```

The caret is not an entirely separate concept. It is essentially a selection whose beginning and end coincide.

---

## 4. What is a `Range`?

A `Selection` contains one or more `Range` objects. For our ordinary editing case, think of a range as four coordinates:

```text
startContainer
startOffset
endContainer
endOffset
```

Consider:

```html
<p>The answer is important.</p>
```

If we select `answer`, a range describes two positions *inside the DOM tree*—not necessarily a pair of string indices.

This matters because a selection can cross multiple nodes:

```html
<p>
  The <strong>answer</strong> is <em>very important</em>.
</p>
```

Rich-text editing requires reasoning about **tree positions**, not just character positions.

---

## 5. Why PlumePilot saves `selectedRange`

The runtime declares:

```js
let activeField = null;
let selectedRange = null;
```

and:

```js
const rememberSelection = () => {
  const selection = window.getSelection();
  if (
    activeField &&
    selection.rangeCount &&
    activeField.contains(selection.anchorNode) &&
    activeField.contains(selection.focusNode)
  ) {
    selectedRange = selection.getRangeAt(0).cloneRange();
  }
};
```

Historical reference:

```text
offline-quiz-runtime.js:246–252
```

Why clone the range? Imagine:

```text
1. Select "correct answer".
2. The selection belongs to the editor.
3. Click the "Yellow" toolbar button.
4. The button receives the interaction.
5. The browser may move focus or selection.
6. The click handler may no longer find the original selection.
```

Relying only on `window.getSelection()` during the click would be unsafe.

Instead, `selection.getRangeAt(0).cloneRange()` acts as a **snapshot of the editing position**.

---

## 6. Why toolbar buttons intercept `mousedown`

The toolbar builder uses:

```js
item.addEventListener("mousedown", (event) => event.preventDefault());
```

Historical reference:

```text
offline-quiz-runtime.js:391–409
```

This tiny detail matters: by default, interacting with a button can move focus to it.

The desired flow is:

```text
selection inside editor
       ↓
toolbar click
       ↓
preserve editing context
       ↓
apply transformation to previous selection
```

PlumePilot uses two complementary protections:

```text
preventDefault on mousedown
+
cloned selectedRange
```

This is **defensive UI programming**: when correctness depends on a selection, do not rely on one incidental browser behavior.

---

## 7. Restoring a selection

Before running a command, `runCommand()` does:

```js
editor.focus();

if (selectedRange && editor.contains(selectedRange.commonAncestorContainer)) {
  const selection = window.getSelection();
  selection.removeAllRanges();
  selection.addRange(selectedRange);
}
```

then:

```js
document.execCommand(command, false, value);
```

Historical reference:

```text
offline-quiz-runtime.js:253–263
```

The flow is:

```text
saved Range
    ↓
focus editor
    ↓
remove current ranges
    ↓
restore saved Range
    ↓
execute command
```

It resembles a small **editing transaction**.

# Part III — Native commands and custom transformations

## 8. PlumePilot's hybrid strategy

The runtime uses two families of operations.

### Browser-managed operations

```text
bold
italic
underline
strikeThrough
insertUnorderedList
insertOrderedList
superscript
subscript
undo
redo
removeFormat
insertText
```

through:

```js
document.execCommand(...)
```

### Custom DOM operations

```text
colored highlights
study mask
checklist semantics
callouts
controlled callout exit
list normalization
sanitization
```

This distinction is instructive. PlumePilot does not attempt to rebuild the browser's entire editing engine, but native commands are also not sufficient for its custom semantics.

---

## 9. `execCommand()` and deliberate technical debt

`document.execCommand()` is now a **deprecated API**, not part of a modern, stable Web editing standard. We should acknowledge that explicitly.

Why use it anyway? For a small offline editor, it offers practical advantages:

- The browser handles complex operations such as bold, lists, and undo.
- It integrates with ordinary `contenteditable` editing.
- Many changes participate in the browser's **native undo history**.

The final advantage is particularly difficult to reproduce correctly through direct DOM mutations.

The rationale is *not*:

```text
execCommand is the recommended modern API
```

It is:

```text
small feature scope
+ verified compatibility with target browsers
+ value of native undo behavior
+ much higher cost of a complete custom editor
------------------------------------------------
pragmatic use of a legacy API
```

**Legacy does not automatically mean broken**, but it does imply risks: browser differences, an uncertain future, unpredictable interactions with `input`/`beforeinput`, and potential differences between native and custom DOM editing.

### Backend analogy

This resembles using a stable legacy dependency in a narrowly scoped service. The useful questions are not merely "Is it old?" but "How much would replacement cost, what guarantees do we need, and how well can we isolate it?"

PlumePilot keeps this dependency relatively contained within the offline quiz runtime.

# Part IV — Range as a transformation tool

## 10. Highlighting is more than changing CSS

PlumePilot implements highlights with a semantic wrapper rather than `execCommand()`:

```html
<span class="highlight" data-color="yellow">
  text
</span>
```

The main helper is:

```js
wrapSelection(editor, className, key, value)
```

Historical reference:

```text
offline-quiz-runtime.js:343–390
```

It first checks for a useful selection:

```js
if (
  !selectedRange ||
  selectedRange.collapsed ||
  !editor.contains(selectedRange.commonAncestorContainer)
) return;
```

An empty selection is not interpreted arbitrarily.

---

## 11. A structural guard: do not cross incompatible blocks

The code contains:

```js
if (
  range.startContainer.parentElement?.closest("div,li,p") !==
  range.endContainer.parentElement?.closest("div,li,p")
) return;
```

PlumePilot rejects a custom wrapper when the selection crosses different blocks.

Wrapping:

```html
<p>first half...</p>
<ul>
  <li>...second half</li>
</ul>
```

inside one `<span>` could produce invalid or surprising structure.

This is a **structural guard**:

```text
selection inside one compatible block
        ↓
allow operation

selection crosses incompatible blocks
        ↓
fail safely
```

It repeats a principle from autoplay and reverse engineering: if we cannot safely preserve structure, do not invent a transformation.

---

## 12. `extractContents()` + `insertNode()`

The main transformation uses:

```js
const contents = range.extractContents();
wrapper.appendChild(contents);
range.insertNode(wrapper);
```

Consider:

```text
DOM before

<p>
  abc [def ghi] lmn
</p>
```

`extractContents()` moves the selected part into a `DocumentFragment`:

```text
DocumentFragment
└── "def ghi"
```

Then:

```js
wrapper.appendChild(contents);
```

produces:

```html
<span class="highlight" data-color="yellow">
  def ghi
</span>
```

And:

```js
range.insertNode(wrapper);
```

inserts it back at the correct position:

```html
<p>
  abc
  <span class="highlight" data-color="yellow">def ghi</span>
  lmn
</p>
```

This is real structural DOM manipulation with `Range`.

---

## 13. Changing an existing highlight's color

Suppose the editor contains:

```html
<span class="highlight" data-color="yellow">
  important concept
</span>
```

The user selects all its text and applies blue.

PlumePilot recognizes:

```js
if (
  startHighlight &&
  startHighlight === endHighlight &&
  editor.contains(startHighlight) &&
  range.toString() === startHighlight.textContent
) {
  startHighlight.dataset.color = value;
  ...
}
```

Instead of nesting another highlight:

```html
<span class="highlight" data-color="yellow">
  <span class="highlight" data-color="blue">
    important concept
  </span>
</span>
```

it updates the existing node. This prevents **unnecessary markup nesting**.

---

## 14. Changing only part of an existing highlight

A harder case starts with:

```text
[yellow: abc DEF ghi]
```

Select only `DEF` and make it blue. The desired result is:

```text
[yellow: abc ]
[blue: DEF]
[yellow:  ghi]
```

not a blue wrapper nested inside yellow.

The code checks whether the new wrapper ended up within an older highlight:

```js
const oldParent = wrapper.parentElement;

if (className === "highlight" && oldParent?.classList.contains("highlight")) {
  const before = oldParent.cloneNode(false);
  const after = oldParent.cloneNode(false);
  ...
}
```

Then it reconstructs three segments:

```text
before
new wrapper
after
```

Here we clearly see that a rich-text editor is a **tree-rewriting system**.

# Part V — Formatting state and the caret

## 15. Active formatting versus formatted text

One of the hardest problems is distinguishing **formatting already attached to text** from **formatting that will be applied to the next typed character**.

For example:

```text
H₂O|
```

If the caret remains inside `<sub>`, subsequent characters may also be subscript.

Similarly:

```text
[yellow highlight: important|]
```

the browser may continue inserting characters inside the highlight span.

But the user's intention may be: "I'm done with this formatting; I want to continue normally."

This motivated the `Escape` shortcut.

---

## 16. Escape as an editing-state reset

The key handler checks:

```js
if (event.key === "Escape") {
```

Historical reference:

```text
offline-quiz-runtime.js:511–545
```

When a non-collapsed selection exists:

```js
if (!range.collapsed) selection.collapseToEnd();
```

The formatted text remains, but the caret moves to the end.

The handler then checks inline commands:

```js
for (const command of [
  "bold",
  "italic",
  "underline",
  "strikeThrough",
  "superscript",
  "subscript",
]) {
  if (document.queryCommandState(command)) {
    document.execCommand(command, false, null);
  }
}
```

Conceptually:

```text
BOLD ON     → BOLD OFF
SUPERSCRIPT → NORMAL
SUBSCRIPT   → NORMAL
```

Escape acts as a small **state-reset command**.

---

## 17. Exiting a highlight is harder

There is no simple equivalent native highlight command.

The caret might physically be inside:

```html
<span class="highlight" data-color="yellow">...</span>
```

To continue typing outside the highlight, PlumePilot must modify the DOM structure.

It identifies the current highlight, creates a range from the caret to its end, extracts the suffix, preserves any trailing text in a cloned highlight, and moves the caret **after** the original highlight.

The central operation is:

```js
const suffix = caret.cloneRange();
suffix.setEnd(highlight, highlight.childNodes.length);
const rest = suffix.extractContents();
```

Then:

```js
const position = document.createRange();
position.setStart(
  parent,
  Array.prototype.indexOf.call(parent.childNodes, highlight) + 1,
);
position.collapse(true);
```

Escape does not simply mean `set color = null`.

It means:

```text
modify tree
+
reconstruct selection
+
choose new caret position
```

# Part VI — Lists and checklists

## 18. A checklist is not an entirely different list

PlumePilot models checklists using ordinary unordered lists:

```html
<ul class="checklist">
  <li>Review definition</li>
  <li class="checked">Review example</li>
</ul>
```

CSS changes their presentation:

```css
.note-editor .checklist {
  list-style: none;
}

.note-editor .checklist > li::before {
  content: "☐";
}

.note-editor .checklist > li.checked::before {
  content: "☑";
}
```

This reuses the semantics of `<ul>`/`<li>`, adding application-specific state:

```text
standard HTML structure
        +
PlumePilot semantic class
        +
per-item state
```

---


## 19. The bullet list → checklist → bullet list bug

One actual development bug followed this sequence:

```text
1. Create a checklist.
2. Exit the checklist.
3. Choose "bulleted list".
4. The browser continues/recreates a line with checklist semantics.
```

Numbered lists did not exhibit the same problem.

This exposes a `contenteditable` difficulty: **the browser has its own implicit representation of the current list**.

We cannot assume that after a command the DOM perfectly matches the app's intended model.

The current solution introduces:

```js
function splitChecklist(editor) {
```

Historical reference:

```text
offline-quiz-runtime.js:270–288
```

It identifies the current `<li>` inside `<ul class="checklist">` and separates it from the checklist.

---

## 20. Anatomy of `splitChecklist()`

Start with:

```text
CHECKLIST
├── A
├── B  ← current item
└── C
```

The code creates:

```js
const normal = document.createElement("ul");
const remainder = list.cloneNode(false);
```

It moves following siblings into `remainder`:

```text
original checklist
├── A
└── B

remainder checklist
└── C
```

Then it removes checked state:

```js
item.classList.remove("checked");
```

and moves the current item into a normal list:

```js
normal.appendChild(item);
```

The result is:

```text
CHECKLIST
└── A

NORMAL UL
└── B

CHECKLIST
└── C
```

Both preceding and following items remain in their original order. The operation does not indiscriminately convert the entire checklist.

---

## 21. Normalize after the command

The bulleted-list button runs:

```js
if (
  command === "insertUnorderedList" &&
  currentNode(target)?.closest("ul.checklist")
) {
  splitChecklist(target);
  return;
}

runCommand(target, command);

if (command === "insertUnorderedList") {
  splitChecklist(target);
}
```

This double check is important:

```text
before command
+
after command
```

The browser itself may transform the DOM when the command runs.

This is the same recurring design pattern we saw elsewhere:

```text
check
↓
operation
↓
re-check / normalize
```

In earlier chapters we used this after an `await`. Here we apply it after native editing.

---

## 22. Why pressing Enter twice is different

Inside a list, most Enter behavior is still controlled by the browser's `contenteditable` engine.

The familiar double Enter on an empty item may exit the list.

PlumePilot does not reimplement the entire native list-editing algorithm. Instead, it corrects the points where its custom `checklist` semantics could spread unexpectedly.

The trade-off is intentional:

```text
browser
→ general list/caret/Enter behavior

PlumePilot
→ checklist semantics
→ normalization
→ checked state
```

Implementing full list editing from scratch would be a much larger undertaking.

---

## 23. Clicking a checkbox without a real `<input>`

Checklist squares are generated by CSS, not native HTML checkbox inputs.

The click handler tests:

```js
const item = event.target.closest(".checklist > li");

if (
  item &&
  editor.contains(item) &&
  event.clientX < item.getBoundingClientRect().left
) {
  item.classList.toggle("checked");
}
```

Historical reference:

```text
offline-quiz-runtime.js:560–570
```

The region to the left of the `<li>` content is treated as the checkbox marker. This is a simple form of **hit testing**.

# Part VII — Callouts as semantic blocks

## 24. A callout is not simply a color

PlumePilot represents a callout as:

```html
<div class="callout" data-kind="important">
  ...
</div>
```

The recognized kinds are:

```text
important
attention
review
```

Structure carries explicit meaning; CSS chooses presentation:

```text
semantics → data-kind
presentation → CSS
```

---

## 25. The non-reversible callout bug

During development, a user interaction revealed a problem: with no text selected, the app could arbitrarily interpret the preceding block as the target.

But an empty selection might simply mean:

> "I want to start a new callout here."

The current `applyCallout()` explicitly distinguishes three cases.

---

## 26. Case A — Already inside a callout

The helper finds:

```js
const existing = node?.closest(".callout");
```

If it already has the requested kind:

```js
if (existing.dataset.kind === kind) {
  existing.classList.remove("callout");
  delete existing.dataset.kind;
}
```

the action toggles the callout off:

```text
Important callout
      ↓ click Important
Normal block
```

If a different kind is selected:

```js
else existing.dataset.kind = kind;
```

we change from Important to Attention without adding a new wrapper.

---

## 27. Case B — Collapsed selection

When:

```js
selection.isCollapsed
```

PlumePilot does **not** arbitrarily transform the previous block.

It creates a new callout:

```js
const callout = document.createElement("div");
callout.className = "callout";
callout.dataset.kind = kind;
callout.appendChild(document.createElement("br"));
```

Then inserts it after the current block or at the end of the editor, creates a new Range, and moves the caret there.

This directly fixes the UX problem found during development.

---

## 28. Case C — Text selected

For a real selection, PlumePilot asks the browser to transform the block:

```js
document.execCommand("formatBlock", false, "div");
```

then applies semantic attributes:

```js
block.className = "callout";
block.dataset.kind = kind;
```

The user's selection clearly identifies the intent:

```text
this block
    ↓
becomes a callout
```

# Part VIII — How do we leave a callout?

## 29. Enter does not always mean the same thing

The key handler has special behavior for Enter:

```js
if (
  event.key === "Enter" &&
  !event.shiftKey &&
  !event.ctrlKey &&
  !event.metaKey
) {
```

It locates the current callout:

```js
const block = currentNode(editor)?.closest(".callout");
```

but does not exit unconditionally.

It checks whether any text remains from the caret to the end of the callout:

```js
const remaining = selection.getRangeAt(0).cloneRange();
remaining.setEnd(block, block.childNodes.length);

if (!remaining.toString().trim()) {
```

The rule:

```text
Enter inside callout before its end
→ ordinary editing inside callout

Enter at the callout's end
→ exit callout
```

makes the behavior predictable.

---

## 30. `insertNormalBlock()`

To leave a callout:

```js
const paragraph = document.createElement("div");
paragraph.appendChild(document.createElement("br"));
block.after(paragraph);
```

Then place the caret inside the new block:

```js
const range = document.createRange();
range.selectNodeContents(paragraph);
range.collapse(true);
selection.removeAllRanges();
selection.addRange(range);
```

Changing the DOM without repositioning the Selection would leave the editor in a broken state. Both must be updated as one logical operation.

# Part IX — Input, shortcuts, and paste

## 31. The toolbar is not the only input source

A robust editor handles:

```text
mouse
keyboard
paste
browser editing engine
programmatic commands
```

PlumePilot defines shortcuts:

```text
Ctrl/Cmd + B → bold
Ctrl/Cmd + I → italic
Ctrl/Cmd + U → underline
Ctrl/Cmd + G → strikethrough
Ctrl/Cmd + E → superscript
Ctrl/Cmd + D → subscript
ESC          → exit formatting
```

The handler normalizes:

```js
const key = event.key.toLowerCase();
```

and maps:

```js
const command = {
  b: "bold",
  i: "italic",
  u: "underline",
  g: "strikeThrough",
  e: "superscript",
  d: "subscript",
}[key];
```

Historical reference:

```text
offline-quiz-runtime.js:546–555
```

---

## 32. Why not use Shift?

The runtime explicitly ignores the shortcut when:

```js
if (event.shiftKey) return;
```

This reduces conflicts with capitalization, text selection, native shortcuts, different keyboard layouts, and combinations already reserved by the browser.

A small editor should expose a limited, predictable shortcut set.

---

## 33. Paste as plain text

The paste handler uses:

```js
editor.addEventListener("paste", (event) => {
  event.preventDefault();
  document.execCommand(
    "insertText",
    false,
    event.clipboardData.getData("text/plain"),
  );
});
```

Why reject clipboard HTML?

Pasting rich HTML could introduce:

```html
<span style="font-family: ...">
<div class="qualcosa">
<a href="...">
<img ...>
```

or much more complicated markup produced by Word, Google Docs, or another webpage.

PlumePilot's policy is:

```text
external paste
    ↓
text/plain
    ↓
structure managed by our editor
```

This is both an architectural simplification and a defensive measure.

---

# Part X — Sanitization: saved HTML is not automatically trustworthy

## 34. Why sanitize our own editor?

We might say: "Our code generated this HTML, so we can just save it."

But content can pass through browser editing behavior, custom DOM transformations, previously saved annotated files, pasting, legacy markup, and later versions.

Furthermore, an annotated HTML file is reloaded in an executable context.

PlumePilot therefore uses:

```js
cleanHtml(source)
```

Historical reference:

```text
offline-quiz-runtime.js:27–60
```

---

## 35. Allowlist rather than blacklist

The sanitizer defines:

```js
const allowed = new Set([
  "B",
  "STRONG",
  "I",
  "EM",
  "U",
  "S",
  "UL",
  "OL",
  "LI",
  "SUP",
  "SUB",
  "BR",
  "DIV",
  "P",
  "SPAN",
]);
```

The question becomes not "Is this element dangerous?" but:

> **Does this element belong to the document format our editor understands?**

Compare:

```text
blacklist
→ try to enumerate everything forbidden

allowlist
→ only accept structures we explicitly understand
```

For a narrowly scoped format, the second approach is easier to reason about.

---

## 36. Attributes are reconstructed too

PlumePilot does not copy arbitrary node attributes.

For `SPAN`, it recognizes only `.study-mask` or `.highlight` with an allowed `data-color`.

For `DIV`, only `.callout` with an allowed `data-kind`.

For `UL`, only `.checklist`.

For `LI`, only `.checked`.

An element such as:

```html
<span onclick="..." style="..." data-random="...">
```

does not retain those arbitrary attributes.

The sanitizer rebuilds a known subset of the DOM.

---

## 37. Conservative sanitization

The code explicitly says:

```js
// Unknown markup is discarded along with its content.
```

Disallowed nodes produce an empty `DocumentFragment`. This is conservative.

A different sanitizer might choose to strip unsupported tags while retaining their text children.

PlumePilot instead refuses to reinterpret markup it does not recognize.

The trade-off is:

```text
maximum content preservation
          vs.
maximum format predictability
```

For a small notes editor with a restricted HTML vocabulary, the latter is reasonable.

# Part XI — Live state and persistable state

## 38. The editor DOM is not the only state

The runtime initializes:

```js
const notes = new Map(...);
```

Every question has a stable key:

```js
noteKey:
  `test:${...}:question:${questionIndex + 1}`
```

The stored model includes:

```text
explanationHtml
observationsHtml
status
```

Thus:

```text
LIVE EDITOR STATE
contenteditable DOM
Selection
Range
activeField

        ↓ input

PERSISTABLE NOTE STATE
Map<noteKey, note>
```

This separation is crucial.

---

## 39. `input` commits to the model

Every editor registers:

```js
editor.addEventListener("input", () => {
  details.dataset.hasNotes = String(
    saveNote(question, field + "Html", cleanHtml(editor.innerHTML)),
  );
});
```

The flow:

```text
editor DOM mutation
        ↓
input event
        ↓
editor.innerHTML
        ↓
cleanHtml()
        ↓
saveNote()
        ↓
notes Map
```

The `Map` becomes the persistable representation. The live editor DOM can be destroyed and recreated during `render()`.

---


## 40. Rerendering and reconstruction

A quiz may be rerendered when the user changes chapters, filters, question order, or resets a view.

The container is replaced:

```js
container.replaceChildren();
```

Then each editor is recreated.

Saved content is restored with:

```js
if (saved[field + "Html"]) {
  editor.innerHTML = cleanHtml(saved[field + "Html"]);
} else {
  editor.textContent = saved[field] || "";
}
```

Thus:

```text
current DOM
≠
permanent source of truth for notes
```

The `notes Map` is closer to a domain data model. The DOM is an editable view of that model.

### Backend analogy

```text
View Model / DOM
      ↓
change event
      ↓
application state
      ↓
rerender
```

even though this application does not use React, Vue, or a reactive UI framework.

# Part XII — Saving annotated HTML

## 41. The file itself becomes the state container

The offline quiz does not need an external database.

When the user selects **Download HTML with notes**, PlumePilot clones the document:

```js
const clone = document.documentElement.cloneNode(true);
```

It serializes the `notes Map`:

```js
Object.fromEntries(notes)
```

encodes it, and places it inside:

```html
<script id="notes-data" type="application/octet-stream">...</script>
```

Then it saves the entire HTML file.

Historical reference:

```text
offline-quiz-runtime.js:689–705
```

The file now simultaneously contains:

```text
UI
JavaScript runtime
quiz data
offline images
notes
review statuses
```

It is a small **self-contained application snapshot**.

---

## 42. Why encode the notes?

The runtime uses `TextEncoder`, `TextDecoder`, `btoa()`, and `atob()` to convert JSON into a textual payload that can safely be embedded in the data element.

Conceptually:

```text
Map
 ↓ Object.fromEntries
Object
 ↓ JSON.stringify
JSON UTF-8
 ↓ Base64
textual payload
```

On load, the process is reversed.

This is **not encryption**. It is encoding.

The goal is to embed the payload without mixing its contents directly into executable script or arbitrary HTML markup.

# Part XIII — Question status is not note formatting

## 43. Two separate models

Each question can also have a personal review status:

```text
🟢 Verified
🟡 Needs review
🔴 To be verified
```

This state is not represented as a color *inside* the note editor.

It lives in:

```js
note.status
```

The runtime can filter questions without parsing or interpreting their note HTML.

This is good semantic separation:

```text
note content
→ controlled HTML

study workflow
→ status enum
```

If we encoded review status only through visual classes or text colors, filtering would be much more fragile.

# Part XIV — The editor as a state machine

## 44. Chapter 07 returns

Even this small editor can be understood as a state machine.

Not necessarily a formally declared FSM, but an interaction of several state properties:

```text
activeField
selection collapsed / expanded
current formatting
current block type
current list type
callout kind
highlight ancestry
focus state
```

Events include:

```text
FOCUS
KEYDOWN
INPUT
MOUSEUP
MOUSEDOWN TOOLBAR
CLICK TOOLBAR
PASTE
CLICK CHECKLIST
```

Guards include:

```text
Does the selection belong to the editor?
Is the selection collapsed?
Does the range span several blocks?
Are we inside a checklist?
Are we inside a callout?
Is the caret at the end of a callout?
```

Actions include:

```text
execCommand
extractContents
insertNode
split list
create block
move caret
saveNote
sanitize
```

A conceptual machine might be:

```text
EDITOR_IDLE
   ↓ focus
EDITOR_ACTIVE
   ├── select text
   │      ↓
   │   RANGE_SELECTED
   │      ↓ toolbar
   │   FORMAT_SELECTION
   │
   ├── caret in callout + Enter at end
   │      ↓
   │   EXIT_CALLOUT
   │
   ├── caret in highlight + Escape
   │      ↓
   │   SPLIT_HIGHLIGHT
   │
   └── input
          ↓
       SANITIZE_AND_SAVE
```

State-machine reasoning is not specific to autoplay. It is a general technique for understanding interactive systems.

# Part XV — A bug as an invariant violation

## 45. Useful editor invariants

We can define properties that should always remain true.

### Invariant 1 — The toolbar affects only the active editor

```text
selectedRange ∈ activeField
```

### Invariant 2 — Saved markup belongs to the allowed vocabulary

```text
saved HTML ⊆ allowed editor schema
```

### Invariant 3 — A normal bullet list does not inherit checklist semantics

Leaving a checklist should not cause a later ordinary list to acquire `.checklist` accidentally.

### Invariant 4 — Empty callout selection is not arbitrary block selection

A collapsed selection must not cause an unrelated preceding block to be transformed.

### Invariant 5 — Ending formatting really ends it

After Escape, subsequent typing should not unintentionally inherit the formatting the user just exited.

### Invariant 6 — Structural transformations preserve a valid caret

After modifying the tree, the caret should occupy a predictable, valid position.

This perspective makes editor bugs easier to classify. Instead of simply saying "the list behaves badly," we can identify **a violation of list-type separation**.

# Part XVI — Undo/redo and editing transactions

## 46. Why undo is difficult

A user expects:

```text
type
→ format
→ insert list
→ change highlight
→ Ctrl+Z
```

to reverse coherent actions.

With `execCommand()`, the browser maintains part of its own undo history.

But custom operations such as:

```js
extractContents()
insertNode()
replaceWith()
appendChild()
```

are not necessarily integrated into that history in the same way across browsers.

This is a central problem of hybrid rich-text editors. They combine:

```text
browser editing history
        +
custom DOM mutations
```

which do not always share one definition of an **editing transaction**.

---

## 47. What a more formal editor might look like

A larger editor might own a transaction model:

```text
before state
    ↓
operation
    ↓
normalized document
    ↓
transaction record
    ↓
after state
```

For example:

```js
{
  type: "SET_HIGHLIGHT",
  range: ...,
  color: "yellow"
}
```

Or it could use a document model independent of the DOM:

```text
Document Model
     ↓
DOM render
```

rather than treating the DOM as model, view, and editing engine at the same time.

That is the direction taken by professional rich-text editors, but it costs far more than PlumePilot's requirements justify.

# Part XVII — `beforeinput` as a possible evolution

## 48. Observe intent before mutation

Modern Web APIs expose:

```text
beforeinput
```

which fires before many changes are applied to an editable host.

A more structured editor can use it to inspect editing intentions such as:

```text
insertText
insertParagraph
formatBold
historyUndo
...
```

before the DOM is mutated.

A possible future architecture might use:

```text
beforeinput
+ Selection / Range
+ DOM normalization
+ transaction layer
```

to reduce dependence on `execCommand()`.

But this would not be a one-to-one replacement. `execCommand("bold")` encapsulates many editing details that a custom implementation would need to handle.

# Part XVIII — Minimal editor versus editor framework

## 49. When should we stop building it ourselves?

The current scope is modest:

```text
two small fields per question
limited formatting vocabulary
offline file
no collaborative editing
no long multiuser document
no plugin ecosystem
```

A custom minimal editor is defensible here.

But consider adding:

```text
editable tables
complex links
drag-and-drop images
nested callouts
arbitrary indentation
robust cross-browser undo history
collaboration
multiuser comments
versioned document schema
```

Complexity would quickly rise.

At that point an established editor framework with its own document model and transaction system might make sense.

The lesson is not "avoid libraries." It is:

> **Choose an infrastructure level proportional to the editor's semantic complexity.**

# Part XIX — Testing a rich-text editor

## 50. Testing the visual result alone is insufficient

Two DOM trees can appear identical but behave differently when the user types next.

For example:

```html
<span class="highlight">abc|</span>
```

may look the same as:

```html
<span class="highlight">abc</span>|
```

But the next character:

```text
x
```

may remain highlighted in the first case and unhighlighted in the second.

Therefore the test target is:

```text
DOM
+
Selection
+
next user action
```

---

## 51. A useful test matrix

### Inline formatting

```text
single-node selection
selection with bold already applied
collapsed selection
Escape after bold
Escape after superscript
Escape after subscript
```

### Highlighting

```text
plain → yellow
yellow → blue on the entire wrapper
yellow → blue on a partial selection
Escape in the middle
Escape at the end
cross-block selection → no transformation
```

### Checklists

```text
new checklist
check/uncheck an item
checklist → bullet
checklist → numbered
exit list → new bullet
split with preceding items
split with following items
split with both
```

### Callouts

```text
selection → callout
collapsed caret → new callout
same kind → remove
kind A → kind B
Enter in the middle
Enter at the end
```

### Persistence

```text
type → change chapter → return
type → filter → return
download annotated HTML → reopen
legacy markup → cleanHtml
paste rich text → plain text
```

### Cross-browser

```text
Chrome
Edge
Firefox
```

With legacy commands especially, we should not assume identical behavior across browsers.

## 52. Test properties, not only examples

Many editor rules can be formulated as properties.


# Part XXII — A possible future architecture

## 55. Separate the DOM adapter from the document model

A much larger editor might separate:

```text
┌───────────────────────┐
│     Note Model        │
│ blocks / marks / list │
└───────────┬───────────┘
            │ render
            ▼
┌───────────────────────┐
│      DOM Adapter      │
└───────────┬───────────┘
            │
            ▼
      contenteditable
            ▲
            │ input intent
┌───────────┴───────────┐
│  Selection Adapter    │
│  beforeinput / Range  │
└───────────────────────┘
```

Operations could be explicit commands:

```text
TOGGLE_BOLD
SET_HIGHLIGHT(yellow)
TOGGLE_CHECKLIST
SET_CALLOUT(attention)
EXIT_FORMATTING
```

That offers greater predictability—but at the cost of building and maintaining an editing engine.

For current PlumePilot, it is probably not worthwhile.

# Part XXIII — Backend analogies

## 56. Selection as an application cursor

We can compare a `Range` with a database or stream cursor that identifies a region of the current structure.

But the DOM can change, so a Range is not a stable business identifier.

It is closer to:

```text
cursor / pointer inside mutable structure
```

than to:

```text
primary key
```

That is why PlumePilot checks that the range still belongs to the intended editor.

---

## 57. `cleanHtml()` as boundary validation

In Chapter 02, `bridge.js` normalized messages crossing a boundary.

The same thing happens here:

```text
arbitrary DOM produced by the editing engine
        ↓
cleanHtml()
        ↓
allowed PlumePilot notes format
```

`cleanHtml()` acts as an **anti-corruption layer** between browser editing DOM and persisted notes.

---

## 58. Is `input` event sourcing? Not really

It may be tempting to describe:

```text
every input event → persisted event
```

but that is not what PlumePilot does.

It stores the **current snapshot** of sanitized HTML, not a sequence of events:

```text
INSERT_TEXT
TOGGLE_BOLD
ADD_CALLOUT
...
```

This is **snapshot persistence**, not event sourcing.
